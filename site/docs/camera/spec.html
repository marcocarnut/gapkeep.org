Pi Camera Module v2.1 (IMX219) on the Pi Zero v1.3: functional specification

This document states the facts needed to write, in C++ on Circle, a driver that powers the Raspberry Pi Camera Module v2.1, configures its Sony IMX219 sensor, receives frames through the BCM2835's CSI-2 receiver ("Unicam", instance 1) into memory, and stops cleanly. It contains facts only (addresses, bit positions, values, orderings, timings) and no code. Where each fact comes from is recorded in PROVENANCE.md. The tags in square brackets say how much a fact can be trusted:

  • [DS]: documented in a public datasheet or schematic (Sony IMX219 datasheet, Raspberry Pi schematics, BCM2835 ARM Peripherals).
  • [RPI]: published by Raspberry Pi as configuration data (dt-blob.dts, Linux device trees, firmware headers).
  • [GPL-FACT]: found only in GPL-2.0 driver sources (Linux bcm2835-unicam.c, vc4-regs-unicam.h, imx219.c, or rsta2/libcamera), with no public document; restated here as bare facts. Expect less certainty about meaning.
  • [CIRCLE]: available in the Circle tree vendored in this repository (GPLv3, the same licence as GapKeep), so it can be used directly.
  • [UNCERTAIN]: inferred; check on hardware.

All addresses are ARM physical addresses on the BCM2835 (peripheral base 0x20000000), unless written as a VideoCore bus address (0x7Exxxxxx for peripherals, or 0x4xxxxxxx / 0xCxxxxxxx for SDRAM).

#1. Recommended mode

640 x 480, RAW8, 2 CSI-2 data lanes, 2x2 analogue ("special") binning of a centred 1280 x 960 crop, about 30 frame/s.

Why:

  • It is a mode the Raspberry Pi firmware itself uses (its "mode 7"). Its window and binning values were captured from the firmware's I2C traffic, so they are proven on this hardware [GPL-FACT]. The PLL, lane and link settings are those used for every 2-lane IMX219 mode on the Pi [GPL-FACT], and they match the datasheet's 2-lane clock example (912 Mbit/s per lane) [DS].
  • RAW8 gives one byte per pixel and needs no unpacking. Unicam writes the pixels as they arrive, so a line is 640 bytes and a frame is 307 200 bytes. The QR decoder needs 8-bit grey, so 10 bits buys nothing. RAW8 is a plain sensor output format, data type 0x2A, CSI_DATA_FORMAT 0x0808 [DS]. Linux offers it for this mode with the same binning [GPL-FACT].
  • Averaging each 2x2 Bayer block gives a 320 x 240 grey image, the size of the default scanner preview (docs/CAMERA.md), at very low CPU cost.
  • The trade-off: the field of view is the central 1280 x 960 of the 3280 x 2464 array, about 39 % of the width. That is a modest zoom: QR codes fill more pixels, but must be held more squarely in front of the lens. A full-field alternative (1640 x 1232 binned, then 2x2 averaged to 820 x 616 grey) costs about 6.6 times the memory bandwidth and CPU per frame. It is listed in section 6.7 as an option.

RAW10 is the fallback if RAW8 misbehaves. Section 6.6 lists the differences: CSI_DATA_FORMAT 0x0A0A, OPPXCK_DIV 10, data type 0x2B, packed 5 bytes per 4 pixels.

Notes:

  • The firmware's default state for GPIO 41 and 32 is output, inactive (low). The camera is therefore unpowered at boot [RPI].
  • GPIO 28/29 and GPIO 0/1 (the HAT ID EEPROM pins on the header) can both be routed to BSC0 with ALT0. Linux switches between them with a pin multiplexer (i2c0mux, pinctrl states i2c0_gpio0 / i2c0_gpio28) [RPI]. Only one pair may be in ALT0 at a time. Otherwise both pin pairs drive the same controller.
  • Circle: CI2CMaster device 0, configuration 1 selects GPIO 28/29 ALT0 with pull-ups [CIRCLE]. rsta2/libcamera uses exactly I2C 0 configuration 1, power GPIO 41 and LED GPIO 32 for the "Zero (v1.3 only)" [GPL-FACT].
  • BSC0 is at 0x20205000 (bus 0x7E205000) [DS].
  • The Zero's camera connector has 22 pins (0.5 mm pitch) and the camera has 15 (1 mm): a Zero-specific adapter cable is needed. The Zero v1.2 has no camera connector at all. On the Zero's connector, CAM_GPIO0 is pin 17, CAM_GPIO1 pin 18, SCL0 pin 20 and SDA0 pin 21 (Pi Zero reduced schematic) [DS].

#2.2 The Camera Module v2.1 board (Raspberry Pi schematic "Raspberry Pi Camera V2.1", rev 2.1, 2018) [DS]

Connector pin (15-way) Signal
2/3, 5/6, 8/9 CSI data lane 0 N/P, data lane 1 N/P, clock N/P
11 ENABLE: drives the enable inputs of all three regulators (1.8 V AP7331-18, 2.8 V AP7331-28, 1.2 V PAM2301)
12 not connected
13/14 SCL/SDA, level-shifted (DMG1024UV) to the sensor's 1.8 V I2C
15 3.3 V
  • The sensor's clock (INCK/MCLK) is a 24 MHz oscillator on the module, powered from the 1.8 V rail with its output enable tied high. The Pi provides no clock.
  • The sensor's XCLR (/PWDN) pin appears tied to the 1.8 V rail. Asserting ENABLE (GPIO 41) therefore powers the rails, starts the oscillator and releases reset, all at once. The tie is read from the schematic drawing [UNCERTAIN in detail, but it has no consequence for the driver].
  • The v2.1 module has no LED: pin 12 (CAM_GPIO1 / GPIO 32) is unconnected. Driving GPIO 32 is harmless, and it lights the LED of a Camera Module v1. camera.h's "the LED goes on" will not be visible with a v2.
  • An ATSHA204A authentication chip shares the I2C bus, on the 3.3 V side. Its usual 7-bit address is 0x64 (Microchip default) [UNCERTAIN]. Ignore it.
  • Linux describes the module as rotation = <180> [RPI]. The sensor is mounted so that its native readout is upside down relative to the module's "up". See section 4.8.

#2.3 Sensor I2C

  • 7-bit slave address 0x10 (datasheet Fig. 10: address bits [7:1] = 0010000) [DS]; Linux DT imx219@10 [RPI].
  • Registers use 16-bit addresses (sent MSB first) and 8-bit data. Writes auto-increment, so a 16-bit register is written as a 4-byte transfer: address high, address low, value high, value low [DS].
  • Reads: a write of the 2-byte address, then a read. The datasheet describes a "dummy write" of the index followed by a read, and says the index is retained between transfers. A STOP between the write and the read is therefore acceptable, and a repeated start is not required [DS]. Reads auto-increment.
  • The interface is CCI, compatible with I2C fast mode / fast mode plus [DS]: 100 kHz and 400 kHz both work. The level shifter's 2.2 kOhm pull-ups favour 400 kHz or less.

#3. Power, clocks and firmware

#3.1 Firmware

  • The SD card boots start.elf (not start_x.elf). GapKeep's config.txt does not set start_x, camera_auto_detect or gpu_mem for the camera. The GPU firmware therefore does not drive the camera or I2C0, and the ARM owns both. Keep it that way: with start_x.elf the GPU's own camera stack may access I2C0 and Unicam [RPI, general knowledge].

  • Linux requires the VPU clock to be at least 250 MHz while Unicam streams (MIN_VPU_CLOCK_RATE) [GPL-FACT]. On the Pi Zero the firmware's default core_freq is 400 MHz and core_freq_min is 250 MHz [general knowledge, UNCERTAIN], so no change is normally needed. Read it once and log it.

All-zero reads suggest the block is unpowered.

#3.3 CAM1 clock (the Unicam "lp" clock), Clock Manager

Register ARM address Bus address
CM_CAM1CTL 0x20101048 0x7E101048
CM_CAM1DIV 0x2010104C 0x7E10104C
  • The layout is the same as the documented general-purpose clocks (BCM2835 ARM Peripherals 6.3) [DS for GP clocks; CAM1 offsets: Linux clk-bcm2835 and Circle ARM_CM_CAM1CTL/DIV [GPL-FACT, CIRCLE]]:
    • CTL: password 0x5A in bits 31:24, MASH 10:9, BUSY 7, KILL 5, ENAB 4, SRC 3:0.
    • DIV: password 0x5A in bits 31:24, DIVI 23:12, DIVF 11:0.
  • For CAM1, Linux declares only 4 integer bits and 8 fraction bits in the divider [GPL-FACT]. Use an integer divider of at most 15.
  • Required rate: 100 MHz (Linux sets the lp clock to 100 MHz before streaming) [GPL-FACT]. Source 6 = PLLD_PER, 500 MHz on Pi 1/Zero, DIVI = 5, DIVF = 0, MASH 0 [DS for the source numbering; CIRCLE gives PLLD = 500 MHz].
  • Circle: CGPIOClock (GPIOClockCAM1 /* = 9 */, GPIOClockSourcePLLD) with Start (5, 0, 0), or StartRate (100000000), does exactly this (control register at CM base + 9 x 8 = 0x48) [CIRCLE]. rsta2/libcamera calls StartRate(100 MHz) on Pi 1-3 [GPL-FACT].
  • Stop it on shutdown: clear ENAB, then wait for BUSY to clear.

#3.4 CSI lane clock gate

Register ARM address Bus address
CAM1 lane clock gate ("clk_gate_base" of csi1) 0x20802004 0x7E802004

(CAM0's gate is at 0x7E802000 [RPI].) This register is not documented publicly; all facts here are [GPL-FACT]:

  • Every write carries the password 0x5A000000 OR'ed with the value.
  • The value is a 2-bit field per lane, clock lane in bits 1:0, then data lane 0 in bits 3:2, data lane 1 in bits 5:4, and so on. Each enabled lane's field is 01.
  • Clock lane + 2 data lanes: write 0x5A000015. Disable all: write 0x5A000000.

#3.5 Interrupt

  • Unicam1 raises GPU (VideoCore) peripheral interrupt 39 (bank 2, bit 7). Linux DT: interrupts = <2 7> [RPI]. Circle: ARM_IRQ_CAM1, and ARM_FIQ_CAM1 = 39 [CIRCLE].
  • The line is level-like: it stays asserted until the status bits are cleared in UNICAM_STA and UNICAM_ISTA (write-1-to-clear, section 5.4).

#4. The IMX219 sensor

#4.1 Identity and constants

#4.2 Power-up and standby (datasheet section 8) [DS]

  • Supplies may rise in any order. XCLR must go high only after all supplies are up (t3 >= 0.5 us). On the v2.1 module all of this follows from GPIO 41 (section 2.2).
  • The internal reset releases within t4 <= 200 us after supplies and XCLR. The sensor must not leave software standby until t5 >= 6 ms after XCLR rises (and t6 <= 32 000 INCK clocks, 1.33 ms at 24 MHz, for silicon init). Linux waits 6.2 ms after power-on before touching the sensor [GPL-FACT]. Allow more for the module's regulators: 10-20 ms after setting GPIO 41 is a safe start [UNCERTAIN margin].
  • After streaming starts, data begins after 1.2 ms + exposure time (t9). D-PHY power-up and init take t7 about 1 ms and t8 about 100 us.
  • mode_select 0x0100: 0 = software standby, 1 = streaming. software_reset 0x0103 bit 0 exists. Linux does not use it [GPL-FACT], and neither should we unless needed [UNCERTAIN: no wait time is documented].
  • Stop: write 0x0100 = 0. If the write lands between frame start and frame end, the current frame is completed first and the sensor then enters standby. If it lands in frame blanking, standby is immediate. Allow one frame time before removing power [DS]. Optional fast standby: 0x0106 = 1, then 0x0100 = 0, and standby follows after the current line [DS].
  • Power-off: XCLR may fall immediately after standby, and supplies may fall in any order [DS]. In practice: standby, wait one frame, GPIO 41 low.
  • Lane state quirk: the sensor does not drive its CSI lanes to LP-11 after power-up until streaming has been started once. Linux therefore starts streaming (0x0100 = 1), waits about 100 us and goes back to standby (0x0100 = 0, then about 100 us) right after detecting the chip, before Unicam is started [GPL-FACT]. Do the same, or Unicam may not synchronise to the first frame.

#4.4 CSI-2 output [DS]

  • Short packets: Frame Start data type 0x00, Frame End 0x01. Long packets: RAW8 data type 0x2A, RAW10 0x2B, embedded data 0x12. The virtual channel is set by CSI_CH_ID (0x0110, default 0). Use VC 0.
  • The sensor sends two embedded-data lines (DT 0x12) after Frame Start, before the image lines. They hold register values in a tagged format. Unicam filters by data type (section 5.3), so with only DT 0x2A selected they are not written to the image buffer.
  • Between lines and frames the lanes go to LP-11. The clock lane stops in blanking: the IMX219's clock is non-continuous. Linux DT says clock-noncontinuous [RPI], and rsta2/libcamera comments "non-continous clock" [GPL-FACT]. This decides the Unicam lane settings in section 5.3.
  • Lanes on the module: connector D0 is the sensor's MD0 and D1 is MD1 [DS]. Linux DT: clock lane 0, data lanes 1 and 2 [RPI]. No lane swapping is needed.

#4.5 Frame timing

  • Time per line = LINE_LENGTH_A / 182.4 MHz = 3448 / 182.4e6 = 18.90 us [DS formula, values GPL-FACT].
  • Frame period = FRM_LENGTH_A x line time. With FRM_LENGTH_A = 1763: 33.33 ms, 30.0 frame/s.
  • In analogue binning mode (BINNING_MODE = 3), the datasheet says FRM_LENGTH_A counts in units of 2 lines [DS]. Linux models this as a doubled pixel rate (364.8 Mpixel/s) and halves the values it writes to FRM_LENGTH_A and COARSE_INTEGRATION_TIME_A [GPL-FACT]. The two descriptions agree when one register unit is taken as LINE_LENGTH_A / 182.4 MHz of real time. An older Raspberry Pi driver wrote 1763 for this mode and called it 30 frame/s; current ones write about 853-881 and call it 60 frame/s [GPL-FACT]. Both fit the rule above. Verify by timing frame-start interrupts. If the measured rate is 15 frame/s, halve FRM_LENGTH_A.
  • Mainline Linux raises the minimum LINE_LENGTH_A to 3560 (0x0DE8) in analogue binning, because 3448 "can cause artefacts with RAW10" (the ADC works on two lines together) [GPL-FACT]. With RAW8, 3448 is what the Pi firmware used. If artefacts (horizontal banding) appear, use 3560 and FRM_LENGTH_A 1708 for 30.0 frame/s (line time 19.52 us).
  • The exposure must stay at most FRM_LENGTH_A - 4. If it is larger, the frame stretches to exposure + 4 lines [DS].
  • Changes to gain and exposure take effect at the next or the following frame without blanking glitches. Changes to binning, vertical flip, vertical window or subsampling cause a longer "no data" gap [DS]. Set those only in standby.

#4.6 Exposure and gain [DS]

Control Register Range Law
Exposure (coarse integration time) 0x015A-0x015B (16 bits) 1 .. FRM_LENGTH_A - 4 (Linux uses minimum 4) T = coarse x line time + fine offset. fine_integration_time (0x0388-0x0389, read only) = 500 pixel clocks, and the offset is fine / 2 pixel-clock periods (negligible)

Use analogue gain before digital gain: digital gain only scales, and coarsens, the numbers. Write each 16-bit value in one auto-incrementing I2C transfer so that the two bytes are latched at the same V-sync.

Address Meaning

  • The pattern generator sits after the analogue chain and before digital gain and black-level adjust (datasheet section 6 data-flow figure). Keep digital gain at 1.0x when checking exact values.
  • The pattern can be switched on and off while streaming. Registers may be set in any order [DS].
  • Colour bars appear as vertical bands of constant value. In grey they show as about 8 bands of different brightness. The exact colour order is drawn in the datasheet figure but not given as text [UNCERTAIN].
  • For exact verification of the data path, two patterns are better:
    • Solid colour (mode 1) with all four test_data values set to the same 10-bit value V. In RAW8 every pixel should then be V >> 2, possibly offset by the black-level stage [UNCERTAIN].
    • The column counter (mode 7), which shows byte order and line stride errors immediately.

#4.8 Orientation and Bayer order

  • IMG_ORIENTATION_A 0x0172: bit 0 = horizontal mirror, bit 1 = vertical flip [DS]. Set it in standby. The vertical flip causes a no-data gap if changed while streaming [DS].
  • The module is mounted rotated by 180 degrees (Linux DT rotation = <180> [RPI]). An upright image therefore needs both flips: 0x0172 = 0x03 [UNCERTAIN: confirm with a real scene]. A 180 degree rotation does not stop QR decoding, but a single mirror does (quirc needs an explicit flip), so never set only one bit.
  • Bayer order of the first pixel of the image for this window [GPL-FACT, from Linux's format table]:
0x0172 Order
0x00 RGGB
0x01 (H mirror) GRBG
0x02 (V flip) GBRG
0x03 (both) BGGR

The 2x2 average used for grey (section 6) does not depend on the order.

#5. Unicam (CSI-2 receiver), instance 1

#5.1 Base and access

  • Unicam1 registers: 0x20801000-0x208017FF (bus 0x7E801000, size 0x800). Unicam0 is at 0x7E800000 [RPI].
  • 32-bit registers. Use read-modify-write where noted.
  • No public Broadcom documentation exists. The register offsets and reset values are corroborated by an independent register list ("rpi-internal- registers", Region CAM1), which names them CAM1_CAMCTL, CAM1_CAMSTA and so on. The bit fields come only from Linux's vc4-regs-unicam.h, which says they were taken from Broadcom's code drops for the BCM21553 and the Rhea/Hawaii/Java Android kernels [GPL-FACT]. Meanings in the tables below that go beyond the bit name are inferred [UNCERTAIN].

#5.4 Frames, interrupts and buffer switching [GPL-FACT, behaviour inferred from Linux's interrupt handling]

  • On each interrupt: read STA and write the value back (clears it). Read ISTA and write it back. If neither STA.IS nor STA.PI0 is set, there is nothing to do.
  • Frame end = ISTA.FEI or STA.PI0 (the packet-compare match on the FE short packet). Frame start = ISTA.FSI.
  • The buffer address is latched at frame start. IBSA0/IBEA0 act as "next frame" registers: whatever they hold when a frame starts is where that frame is written. LIP forces a load at start-up.
  • Therefore program the next buffer after a frame start (and, as a fallback, on a line-count interrupt), never at frame end. Linux says the hardware may not take the new address if a new frame has already started [GPL-FACT].
  • If FE and FS arrive in one interrupt, handle FE first.
  • A frame is complete at FE, in the buffer that was latched at the preceding FS.
  • The receiver cannot be paused while the sensor streams. When no free buffer is available at FS, Linux points IBSA0/IBEA0 at a dummy buffer with end = start (size 0), so the hardware keeps writing into a harmless place [GPL-FACT; exactly how the hardware behaves at end = start is UNCERTAIN, so give the dummy buffer one page of real memory]. A simpler scheme for us: three buffers in rotation (being written, being latched next, owned by the consumer). If the consumer still holds a buffer, reprogram the same "next" buffer, which drops that frame.
  • Line-count interrupts (LCIE) arrive every N lines. They are not needed for correctness. LCIE = 0 turns them off [UNCERTAIN], or ignore them.
  • IBWP reads the current write address: (IBWP - IBSA) / stride = lines written so far.
  • Error indications worth logging (not clearing as errors): STA.IFO, OFO and BFO (FIFO overflows: bus or VPU clock too slow), SBE/PBE/CRCE/PLE (link errors: timing settle values or signal integrity).

#5.5 Alignment and memory

  • Line stride (IBLS): Linux rounds bytes-per-line up to a multiple of 32 [GPL-FACT]. 640 already is.
  • Start addresses: use at least 32-byte (cache-line) alignment. Page (4 KiB) alignment is what Linux's allocator gives [GPL-FACT for Linux usage; the hardware minimum is UNCERTAIN, at least 16 bytes].
  • IBSA/IBEA are VideoCore bus addresses. On the Pi 1/Zero with the GPU L2 cache enabled for the ARM (Circle's default), SDRAM is seen by devices at the 0x40000000 alias. Circle's BUS_ADDRESS() produces the right alias for the build configuration [CIRCLE].
  • Frame size RAW8 640 x 480 = 307 200 bytes (300 KiB). Three buffers take about 900 KiB.
  • Bandwidth: 640 x 480 x 30 = 9.2 MB/s, trivial for the bus.

#6. Data format and grey conversion

#6.1 RAW8 in memory

  • One byte per pixel, pixels in sensor order left to right, lines top to bottom, each line starting at IBSA + line x IBLS. With 640 pixels and stride 640 there is no padding.
  • Values are the top 8 bits of the 10-bit ADC result after digital gain, with the black level at 16 [DS].

#6.2 RAW10 in memory (the fallback; IPIPE = 0)

  • MIPI CSI-2 RAW10 packing: every 5 bytes hold 4 pixels. Bytes 0-3 are bits 9:2 of pixels 0-3. Byte 4 holds the 2 low bits: pixel 0 in bits 1:0, pixel 1 in bits 3:2, pixel 2 in bits 5:4, pixel 3 in bits 7:6 [MIPI CSI-2 RAW10 definition, public in V4L2 documentation of the packed 10-bit Bayer formats].
  • A 640-pixel line is 800 bytes (a multiple of 32). For 8-bit grey, ignoring every fifth byte is enough.
  • The black level is 64 (in 10-bit units) [DS].
  • Alternatively, Unicam can expand to 16 bits per pixel: IPIPE PUM = 4 (unpack10), PPM = 5 (pack16). The line is then 2 x width bytes [GPL-FACT].

#6.3 Bayer to grey

  • The image is a Bayer mosaic, 2 x 2 tiles of one red, two green, one blue (section 4.8 gives the order). For one grey pixel per tile, take the average of the four values (sum >> 2). That is roughly luminance and independent of the order, so flips do not need special cases. A 640 x 480 RAW8 frame becomes 320 x 240 grey.
  • Optional: subtract the black level (16 in RAW8), clamping at 0, and stretch, so that black reads as 0.
  • A more luma-like weighting (for example R x 0.3, G x 0.59, B x 0.11) needs the Bayer order and gains nothing for QR codes. Under strongly coloured light the plain average is the more robust choice.
  • Read the buffer only after FE and after the cache maintenance in section 8.

#6.4 Colour bars through this path

In grey, bars appear as vertical bands of constant value 320 / 8 = 40 pixels wide, if the pattern spans the whole output [UNCERTAIN: the TP_WINDOW registers are set to 1640 x 1232 for this mode].

#6.5 Embedded data

Not captured: IDI0 selects only DT 0x2A, and DCS = 0.

#7. Auto-exposure (the sensor has none)

Controls: exposure lines E (1 .. FRM_LENGTH_A - 4), analogue gain code A (0..232, gain 256 / (256 - A)), digital gain D (1.0..16). Total brightness is roughly proportional to E x gainA x gainD, minus the black level. New values take effect one or two frames after they are written [DS], so measure, change, and then skip two frames before measuring again.

Suggested algorithm, in prose:

  1. Measure on the grey image you already compute: the mean over a central region (for example the middle half), excluding the black level, plus a bright-percentile estimate (for example the 95th percentile from a 64-bucket histogram) to catch clipping. Sub-sampling every 4th pixel is plenty.
  2. Target: mean grey about 0.4-0.5 of full scale. If more than about 2 % of pixels are at 255, lower the target. QR codes need contrast, not brightness, so slight underexposure is better than clipping.
  3. Correct the total exposure product by target / measured, limited per step (for example between x0.5 and x2) and damped (move about half-way in log terms) to avoid oscillation. Treat a measurement of almost nothing as "multiply by 2".
  4. Distribute the product in this order:
    • Exposure time first, up to a motion-blur cap. A handheld code wants 10-15 ms, about 530-800 lines at 18.9 us.
    • Then analogue gain up to about 8x (code 224).
    • Then exposure up to the frame limit.
    • Digital gain last.
    • Going darker, reduce in the reverse order.
  5. Write exposure and gains right after a frame-end interrupt (in frame blanking), each 16-bit value in one I2C transfer, so that all values are latched at the same V-sync.
  6. Optionally, in very dark scenes, lengthen FRM_LENGTH_A (lower frame rate) to allow longer exposures. FRM_LENGTH_A may change while streaming because it is a frame-bank register, but changes take effect with a delay.

Start values: E = 800 lines, A = 0, D = 1.0. Convergence then takes a few frames.

#8. Known pitfalls

  1. Cache coherency (ARM1176, 32-byte L1 lines). Unicam writes SDRAM behind the CPU's data cache.
    • Align buffers to 32 bytes and size them in whole cache lines.
    • Before handing a buffer to Unicam, clean and invalidate its range. Then never write it from the CPU while Unicam may.
    • After FE, before reading, invalidate its range again (Circle's CleanAndInvalidateDataCacheRange is the available primitive on the Pi 1 [CIRCLE]). Reading a buffer with no dirty lines makes this safe.
    • Alternatively, use non-cached (coherent) memory, which is slow for the CPU's 2x2 pass. Circle's coherent region is small and shared, so cached buffers with maintenance are preferable.
    • Use DataSyncBarrier/DataMemBarrier around register writes that publish buffer addresses.
  2. Bus addresses. IBSA/IBEA take VideoCore bus addresses, not ARM physical addresses: use Circle's BUS_ADDRESS().
  3. LP-11 at start-up. The IMX219 does not enter LP-11 until it has streamed once. Do the stream-on/stream-off toggle after power-up (section 4.2), or the receiver may not sync.
  4. Non-continuous clock. Do not enable HS termination (CLHSE/CLTRE, DLHSE/DLTRE) for this sensor. Linux enables those only for continuous-clock sensors [GPL-FACT].
  5. Missing frame ends. Without the CMP0 packet-compare on the FE short packet, frame-end interrupts can be missed [GPL-FACT]. Treat STA.PI0 as a frame end.
  6. Buffer switch timing. Program the next address after FS, not at FE. A new address written too late is silently not used for the following frame.
  7. Never leave Unicam without a valid buffer while the sensor streams. It cannot be paused and will write wherever IBSA points.
  8. Stop order. Stop the sensor first, then Unicam (section 5.6). Do not free buffers before CPE is cleared.
  9. VPU clock. Below 250 MHz, Unicam's FIFOs may overflow (STA.IFO/OFO) [GPL-FACT].
  10. I2C pin mux. Do not leave GPIO 0/1 in ALT0 while using GPIO 28/29 for BSC0.
  11. Wrong firmware. start_x.elf, or camera_auto_detect=1 / start_x=1 in config.txt, lets the GPU firmware talk to the camera.
  12. Power-up time. Talking to the sensor sooner than about 6 ms after GPIO 41 rises fails (NAKs, or a chip ID of 0).
  13. 16-bit register tearing. Write MSB and LSB in one transfer. Values straddling a V-sync give a one-frame glitch.
  14. Orientation. Set 0x0172 before streaming. A single mirror makes QR codes unreadable.
  15. Hardware variants. Some third-party "v2" modules (clones) differ: other oscillators, an LED on pin 12. The chip-ID check (0x0219) catches non-IMX219 modules, such as a v1 (OV5647, address 0x36) or a v3 (IMX708, unsupported).
  16. Unpowered block. If register reads return 0 instead of the reset values (ANA 0x777, CLK 0x2), the power domain or clock is off.

#9. Main uncertainties

  • Meanings of several Unicam bits (MEM, IBOB, MISC FL0/FL1, the PRI fields, the units of the CLT/DLT timing values). The values to write are known [GPL-FACT]; the reasons are not.
  • The real frame rate for a given FRM_LENGTH_A in analogue-binned mode (30 vs 60 frame/s for 1763 lines; section 4.5). Measure it.
  • Whether tag 0x00038030 is needed or supported on the firmware in use. Detect with the reset-value check.
  • Which flip makes the image upright on a real module (expected 0x03).
  • The test-pattern window registers in this mode (copied from the firmware trace) and the exact bar order.
  • The 12 undocumented 0x4xxx register values: required by convention, with unknown effect.
